# 吃什么饭 · V1 需求文档

状态：讨论稿。本文件定义 V1 要做什么、不做什么以及验收标准；技术选型见 [TECH_STACK.md](../architecture/TECH_STACK.md)，目录规划见 [PROJECT_STRUCTURE.md](../architecture/PROJECT_STRUCTURE.md)。

逐页面设计、AI 设计图提示词与逐 API 设计见 [V1 设计书索引](../design/README.md)。设计初稿新增的字段上限、厨房版本控制等细化取舍在索引中单独标明，业务尚未实现。

## 1. 目标与范围

“吃什么饭”V1 是一个纯文字的家庭菜谱应用（不含图片、视频），解决三件事：

1. 把家里常做的菜整理成可查、可搜的菜谱库。
2. 做饭时手机选好菜，厨房里的屏幕只显示这几道菜的做法，手不用碰手机。
3. 不知道今天做什么时，从已有菜谱随机推荐一道，不想吃就“换一个”。

V1 范围：

| 类别     | 功能       | 说明                                                                 |
| -------- | ---------- | -------------------------------------------------------------------- |
| 用户功能 | 菜谱一览   | 列表、搜索、按标签筛选                                               |
| 用户功能 | 菜谱详情   | 食材、步骤、备注                                                     |
| 用户功能 | 随机菜谱   | 主动随机推荐一道已有菜谱，支持“换一个”                               |
| 用户功能 | 做饭历史   | 查看做过的菜并打开最新菜谱；厨房完成自动记录，也可手动记录和删除误记 |
| 用户功能 | 发送到厨房 | 手机勾选多道菜 → 厨房屏只显示这些菜                                  |
| 管理功能 | 菜谱管理   | 新增、编辑、删除、JSON 批量导入                                      |

“用户功能”和“管理功能”是页面职责的划分，V1 不做权限区分，所有页面在同一个 Web 应用内，使用后端默认用户（见 TECH_STACK 第 5 节）。

### 1.1 V1 不做的事

- 图片（封面、步骤图）、视频、音频、计时器、语音播报。纯文字能把数据模型、导入和厨房屏链路先跑通；图片上传、压缩、存储、备份是一整块独立工作，放到 V2。
- 登录、注册、多账号、权限。
- 评论、评分、收藏、购物清单、营养计算。
- 从网页 URL 自动抓取菜谱、AI 生成菜谱。
- Excel / CSV 导入（见第 6 节的理由）。
- 多个厨房设备同时各自显示不同内容。
- 离线编辑与同步。
- 随机外卖、店铺/菜品分享链接管理（明确安排在 V2，见 10.1）；随机菜谱不是系统通知或后台定时推送。

这些不是永久排除，而是 V1 不做；第 10 节记录了可能的后续方向。

## 2. 使用场景

| 场景         | 流程                                                                                              |
| ------------ | ------------------------------------------------------------------------------------------------- |
| 周末翻菜谱   | 手机打开应用 → 浏览列表或搜索 → 看详情决定做什么                                                  |
| 不知道吃什么 | 手机点“今天吃什么？随机推荐” → 看推荐菜名 → 不想吃点“换一个” → 查看做法，决定后再发送厨房         |
| 做饭         | 手机勾选今晚要做的 2～3 道菜 → 点“发送到厨房” → 厨房屏自动显示菜单 → 在厨房屏上切换当前菜、翻步骤 |
| 录入新菜     | 手机或电脑浏览器打开新增页面 → 填表单 → 保存                                                      |
| 批量录入     | 用 AI 工具或手写把若干菜谱整理成 JSON 文件 → 上传 → 看校验结果 → 导入                             |
| 修正         | 发现错字或分量不对 → 进详情页 → 编辑 → 保存                                                       |

## 3. 终端与设备

| 终端              | 用途                   | 说明                                   |
| ----------------- | ---------------------- | -------------------------------------- |
| 手机（主）        | 浏览、搜索、选菜、录入 | PWA，手机布局为基准                    |
| 平板 / 桌面浏览器 | 浏览、录入             | 自适应，不做专门管理端                 |
| 厨房屏            | 只读显示当前菜单       | 闲置 Android 平板，常插电，详见第 7 节 |

## 4. 数据模型（需求层面）

精确字段以 `packages/shared` 中的 Zod Schema 为准；这里定义业务含义和必填性。

### 4.1 菜谱 Recipe

| 字段                      | 必填            | 说明                                                                 |
| ------------------------- | --------------- | -------------------------------------------------------------------- |
| title                     | 是              | 菜名，1～50 字                                                       |
| description               | 否              | 一两句介绍                                                           |
| servings                  | 默认 1          | 原菜谱几人份，正整数；允许记录原本的 2 / 4 人份，不强制转换成 1 人份 |
| prepMinutes / cookMinutes | 否              | 准备 / 烹饪时间，分钟                                                |
| difficulty                | 否              | 简单 / 中等 / 复杂                                                   |
| tags                      | 否              | 字符串数组，如 “家常菜”“汤”“快手”“川菜”                              |
| ingredients               | 是（至少 1 条） | 见 4.2                                                               |
| steps                     | 是（至少 1 条） | 见 4.3                                                               |
| tips                      | 否              | 注意事项、替代方案、家里的经验                                       |
| source                    | 否              | 来源，如书名、网址、“奶奶教的”                                       |
| createdAt / updatedAt     | 系统            | 用于排序                                                             |

V1 用 tags 代替分类表：没有分类管理页面，筛选项由现有菜谱的 tags 汇总得到。等 tags 乱到需要治理时再引入分类管理。

V1 不含任何图片字段。未来加图时在 Recipe 上新增可选的 coverImage、在 Step 上新增可选的 image，老数据不受影响。

### 4.2 食材 Ingredient

| 字段              | 必填      | 说明                                                         |
| ----------------- | --------- | ------------------------------------------------------------ |
| name              | 是        | 食材名                                                       |
| amount            | 否        | 数量，字符串（允许 “适量”“少许”“2～3”）                      |
| unit              | 否        | 克 / 个 / 勺 等，自由文本                                    |
| note              | 否        | 如 “切丁”“提前泡发”                                          |
| group             | 否        | 分组名，如 “腌料”“酱汁”；没有则属于默认组                    |
| scaleWithServings | 默认 true | 是否随目标份数换算；煎炒用油等可关闭，即使是数字也保留原用量 |

amount 仍用字符串，兼容家常菜模糊量词。V1 增加保守的份数换算：只有明确的纯数字（如“200”“0.5”）且 scaleWithServings=true 时，按“目标份数 ÷ 原份数”计算；“适量”“少许”“2～3”“1/2”等保持原文，不猜测或解析部分数字。

所有计算量标注“参考用量，调料按口味调整”；有些油、水、调料受锅具和做法影响，并非严格线性。步骤、tips、烹饪时间不自动换算，尤其步骤中的数量仍是原菜谱说明。查看时换算不修改保存的原用量。

### 4.3 步骤 Step

| 字段  | 必填 | 说明            |
| ----- | ---- | --------------- |
| order | 是   | 顺序，从 1 开始 |
| text  | 是   | 步骤描述        |

### 4.4 厨房会话 KitchenSession

默认用户只有一条记录，表示“厨房屏现在应该显示什么”。

| 字段           | 说明                                                                              |
| -------------- | --------------------------------------------------------------------------------- |
| recipeIds      | 本次要做的菜，有序数组，0～10 条                                                  |
| items          | 与 recipeIds 同序的 `{ recipeId, targetServings }` 数组，每道菜保存自己的目标份数 |
| activeRecipeId | 当前展开的菜，必须属于 recipeIds，或为空                                          |
| updatedAt      | 变更时间                                                                          |

厨房屏上的两类写操作都落在这条记录上：切换当前菜更新 activeRecipeId且保留各菜份数；全部完成把 recipeIds与items清空。会话items保存目标，recipeIds是其派生顺序；原菜谱份数及用量不受完成影响。

## 5. 功能需求

### 5.1 菜谱一览

- 列表项：菜名、tags、总时长（prep + cook，缺失则不显示）、description 前一行。没有图片，所以用排版区分层级：菜名加粗大字，tags 和时长用小字一行。
- 默认按 updatedAt 倒序。
- 搜索：按菜名模糊匹配；V1 不搜食材和步骤正文。
- 筛选：按单个 tag 筛选；筛选项来自现有菜谱 tags 汇总。
- 触底自动加载下一页，每页 20 条（Vant 的 List 组件即可）；搜索词或筛选条件变化时重置到第一页。家庭菜谱量在百级，不做虚拟滚动。
- 空状态：没有菜谱时给出“去新增”入口。
- 多选模式：长按或点“选菜”进入，勾选后底部出现“发送到厨房（N）”。
- 明显提供“今天吃什么？随机推荐”入口，结果在列表页推荐区显示，不另建独立页面，规则见 5.7。

### 5.2 菜谱详情

- 菜名、description、servings、时间、difficulty、tags。
- 食材按 group 分组展示，无 group 的放最前。
- 步骤按 order 展示，编号明显。
- tips、source 放末尾。
- 详情显示“原菜谱 N 人份”与“− / 目标 M 人份 / ＋”，初始目标等于原份数；改份数只更新参考食材量。目标不得低于 1，人份为整数；个/枚食材可能出现小数，不自动向上取整，提示按实际分配。
- 操作：编辑、删除（二次确认）、发送到厨房（单道，等价于把该菜设为本次菜单）。
- 不存在的 id 显示“菜谱不存在”，不显示错误堆栈。

### 5.3 发送到厨房（手机侧）

- 从列表多选或详情页触发，调用 API 覆盖本次菜单与每道菜的目标份数；activeRecipeId 设为第一道。详情入口带上当前调整值；列表多选默认各菜原始份数，在发送弹层内可逐道用 − / ＋ 调整，不要求整桌菜同一个人数。
- 发送成功后提示“厨房屏将在几秒内更新”。
- 提供“查看当前厨房菜单”“清空厨房”入口（V1 可以放在“发送到厨房”的确认弹层里）。“查看当前厨房菜单”是打开时读一次，显示本次菜单和当前在做哪道；没有菜单时显示“厨房当前没有菜单”。
- 手机端是被动的：不轮询厨房状态，不推送，不弹通知。厨房完成后手机上什么都不会发生，只有下次主动打开“查看当前厨房菜单”时才看到已经空了。再次发送前展示当前菜单；非空时明确提示将替换，不能把新选择当成追加。
- 不需要知道厨房设备是哪一台；V1 只有一台厨房屏，不做设备配对。
- 手机“清空厨房”只取消当前菜单，不生成做饭历史；厨房“完成”才同时记历史并清空，两种动作分开。

### 5.4 厨房显示（厨房屏侧）

独立路由（如 `/kitchen`），在厨房设备浏览器中打开并加到桌面即可。

- 轮询 `GET /api/kitchen/session`，间隔默认10秒（`.env`可配置）；只有可见内容（菜单、当前菜、菜谱正文）与本地状态不同时才重绘。只比updatedAt不够：厨房自己写回后读到同一数据不应重绘；只比菜谱id也不够，同一道菜改做法也要更新。“数据没变就不动页面”用于保留阅读位置，不为未来设备提前维护黑白主题。
- 有菜单时通过 Screen Wake Lock API 保持屏幕常亮；没有菜单时释放，让平板按系统设置自动熄屏（见 7.2）。
- 没有菜单时显示待机页：日期、“在手机上选菜后这里会显示做法”。
- 有菜单时：
  - 按会话保存的各菜 targetServings 显示对应参考用量、目标份数与原份数，不在厨房增加份数修改按钮。返回其他菜或重新打开厨房页也保留已发送的份数。
  - 顶部为本次菜单条，列出所有菜名，当前菜用奶油黄底、深色粗边框和“当前”文字标识，不只依赖颜色。点菜名可直接跳到那道菜。
  - 主体显示当前菜的内容，采用翻页而不是长滚动。单道短菜谱能完整放下时合并食材、步骤与 tips，底部只留“完成”；其余竖屏先食材后步骤，超长食材、步骤和 tips 可续页，不能裁掉内容。横屏按两栏呈现。具体分页与按钮规则见厨房画面设计书。
  - 所有操作都是按钮，不做滑动手势。底部固定一排大按钮，按当前位置只显示有意义的那几个：
    - 「上一页」：不在第一道菜的第一页时显示。
    - 「下一页」：当前菜还有后续页时显示。
    - 「下一道：xxx」：当前菜已到最后一页、后面还有菜时显示，代替「下一页」；点击切到下一道菜的第一页。
    - 「完成」：最后一道菜的最后一页显示，代替「下一页」。
  - 只发送一道菜且食材、步骤一页放得下时，底部只有一个「完成」按钮，顶部菜单条也只有一个名字。
  - 切换当前菜时写回 activeRecipeId；点「完成」同事务记录整份菜单的做饭历史并清空 KitchenSession，成功后显示“今天的菜做完了”完成页，几秒后回到待机页。菜单成员都按本次目标份数记为做过，不从翻页推断逐道完成。
- 采用与手机同系的可爱Memo风格，保留大字/大按钮/高对比；可用轻微卡片阴影，不使用动画、渐变或闪烁，不只靠颜色表达状态。
- 不要求在厨房屏上操作其他功能；屏上只有翻页、菜单切换、完成。

「完成」不恢复原菜单；误点后可在手机重新发送，并在做饭历史删除误记，删除历史不恢复厨房菜单。「完成」按钮和「上一页」之间留足间距，避免误点。

为什么用轮询而不是 WebSocket / SSE：只有一台设备、10 秒延迟可接受、实现和排错最简单，旧平板浏览器兼容性也最稳。日后需要即时刷新再换 SSE。

### 5.5 新增 / 编辑菜谱

- 同一个表单组件用于新增与编辑。
- 食材、步骤为动态列表，支持增删和调整顺序（上移 / 下移即可，不要求拖拽）。
- 新增时原份数默认 1，编辑时保留已有原份数；每条食材含“随份数换算”开关，默认开启，文字量仍不自动计算。修改原份数不会自动重写录入用量，表单明确“请按原份数填写用量”。
- 校验：前端用共享 Schema 做提交前校验并在字段旁提示；后端同样校验。
- 保存成功后跳转到详情页。
- 删除菜谱时连同其食材、步骤一起删除；若该菜在厨房会话中，同时从会话里移除。

### 5.6 JSON 批量导入

- 入口：管理区“批量导入”页。上传一个 `.json` 文件，或直接粘贴 JSON 文本。
- 文件结构：

```json
{
  "version": 1,
  "recipes": [
    {
      "title": "番茄炒蛋",
      "servings": 2,
      "cookMinutes": 10,
      "difficulty": "easy",
      "tags": ["家常菜", "快手"],
      "ingredients": [
        { "name": "鸡蛋", "amount": "3", "unit": "个" },
        { "name": "番茄", "amount": "2", "unit": "个", "note": "切块" },
        { "name": "盐", "amount": "适量" }
      ],
      "steps": [
        { "order": 1, "text": "鸡蛋打散，加少许盐。" },
        { "order": 2, "text": "热油下蛋液，凝固后盛出。" },
        { "order": 3, "text": "下番茄炒出汁，倒回鸡蛋翻匀。" }
      ],
      "tips": "番茄先用开水烫一下更容易去皮。"
    }
  ]
}
```

- 每条 recipe 的结构与“新增菜谱”请求体完全一致，复用同一个共享 Schema。V1 纯文字，所以“手动新增”和“批量导入”的数据完全对等，不存在导入后还要补内容的情况。
- 流程：上传 → 服务端整体校验 → 返回校验报告（第几条、哪个字段、什么问题）→ 全部通过才写入；任一条失败则整批不导入。
- 与现有菜谱同名视为冲突并报错，避免同一文件被导入两次；用户改名或删掉重复项后重新导入。
- 单次最多 100 条，文件 ≤ 1 MB。
- 导入成功后显示导入了几条，并链接到列表。
- 在 `docs/examples/` 提供一份可直接导入的示例文件。

### 5.7 随机菜谱

- 用户主动点击“随机推荐”，从服务端默认用户**全部已保存菜谱**中等概率选一道。忽略列表当前搜索/标签，不只从已加载的20条里挑；没有AI生成、系统推送通知或每日定时任务。
- 展示推荐菜名、已有标签/时长/简介及“查看做法”“换一个”。查看做法进入既有详情，目标份数默认该菜原份数，可按原规则调整后发送厨房。
- “换一个”仅排除当前推荐的id；至少两道菜时下一个不与当前相同，但可再次推荐更早出现过的菜。不保存推荐历史，不保证每轮遍历所有菜，不按饮食偏好或做饭记录加权。
- 首次无菜谱时显示“还没有菜谱，先新增或导入再随机推荐”，给新增/导入入口；只有当前一道时，“换一个”提示“没有其他可推荐的菜谱”，保留当前结果，不假装换成新菜。
- 请求中禁止重复点击；网络/服务失败显示可重试错误，不伪装成没有菜谱，换菜失败保留上一道。候选已被删除时详情按既有404处理，不展示假做法。
- 推荐只读，不改菜谱、不改变多选状态、不自动发送或清空厨房菜单。手机仍不轮询、不接收厨房完成通知。

### 5.8 做饭历史

- 目的：买一次食材分几顿做时，从最近做过的菜直接找回菜谱。菜谱一览“更多 → 做饭历史”进入，按做饭时间倒序，每页20次触底加载，不是浏览/随机推荐记录或食材库存。
- 厨房“完成”自动记录本次整份菜单为一顿；只发送、切菜、翻页、替换或手机清空不算做过。记录历史与清空必须同事务成功，版本冲突和失败不能部分写入。
- 不使用厨房屏时，菜谱详情“记录做过”确认后手动记一道，保存当前目标份数。默认记服务器当前时间；V1不做补录过去日期、历史编辑、统计或长期饮食分析。
- 每次保留时间、当时菜名、目标份数与来源（厨房完成/手动）；同一道同一天做多次允许多条。点击打开最新菜谱，并以这次记录的目标份数初始化详情，不保存完整旧做法。
- 修改菜谱不改历史菜名；原菜谱删除后保留历史时间/名字/份数，标“菜谱已删除”，不能再打开做法。
- 支持删除误记的一次完整历史，删除前确认；一顿多菜整组删除，不删除菜谱、不恢复或清空厨房，不提供清空全部。历史持久保留至用户删除。
- 请求中防连点，失败保留内容、明确重试；写入结果不明先查看历史，不盲重提。手机仅主动打开历史读取，不轮询、不推送厨房通知。

## 6. 为什么选 JSON 而不是 Excel

| 对比项                               | JSON                                                                    | Excel                               |
| ------------------------------------ | ----------------------------------------------------------------------- | ----------------------------------- |
| 嵌套结构（一道菜多条食材、多条步骤） | 天然支持                                                                | 需要多 Sheet 或约定分隔符，容易出错 |
| 校验                                 | 直接复用共享 Zod Schema，报错能精确到字段                               | 需要先解析再映射，错误定位困难      |
| 依赖                                 | 零额外依赖                                                              | 需要 xlsx 类库，体积大、维护成本高  |
| 手写成本                             | 对开发者低；对家人高                                                    | 对家人低                            |
| 与 AI 工具配合                       | 把菜谱照片或网页丢给 ChatGPT / Copilot，让它按示例输出 JSON，几乎零成本 | 可行但不如 JSON 稳定                |

结论：V1 用 JSON，成本最低且和代码里的 Schema 完全一致。如果以后家人需要自己批量录入，再考虑“Excel 模板 → 服务端转 JSON → 走同一条导入链路”，导入核心逻辑不用改。

## 7. 厨房屏设备方案

### 7.1 结论：用手头闲置的 Android 平板

V1 的厨房屏就是一个只读网页，跑在任何带浏览器的设备上都一样。为它专门买一台墨水屏不划算：几百到上千块，换来的只是省电和强光下好看一点，而程序本身极简单。手头已经有一台闲置 Android 平板，直接用它，成本为零。

这台平板还有第二个用途：后续计划做的 TodoList 项目要在门口放一块屏显示“今天还有什么没做”，用的是完全相同的模式——固定路由、轮询、大字、按钮操作、常亮或点亮。厨房屏把这套“家庭显示屏”模式跑通，门口屏直接复用（见第 10 节）。

曾经评估过的其他方案：

| 方案                                           | 结论                                                                                        |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------- |
| Android 墨水屏平板（Boox / Meebook 等 7.8 寸） | 体验最合适，但价格对这个用途来说过高；纯文字 + 7.8 寸竖屏的估算仍然成立，未来想升级时按此选 |
| Kindle 等阅读器                                | 浏览器太弱，不考虑                                                                          |
| DIY 电子纸（ESP32 + 墨水屏模组）               | 需要服务端渲染成图片推送，另一条开发线，长期探索方向                                        |

### 7.2 续航与常亮

闲置平板最大的现实问题是电池老化。思路是：**不靠电池，靠插电；不让屏幕一直亮，让它需要时亮。**

1. **常插电，限制充电上限。** 厨房屏固定摆放，插着电用是正常状态。老电池长期保持 100% 会加速鼓包，优先用系统自带的充电上限（三星“保护电池”85%、小米 / 华为的“智能充电”、部分系统在开发者选项里）；系统没有的话，用定时插座每天只充几个小时，待机时平板耗电很低，撑到下一次充电没问题。
2. **屏幕是耗电大头，空闲就熄屏。** 待机页（没有菜单）时不需要亮屏。用 Android 自带的屏幕超时即可：没菜单时几分钟后自动熄屏，进厨房点一下屏幕就亮。有菜单时由网页用 Screen Wake Lock API 保持常亮，菜单清空后释放，让系统按超时正常熄屏。
3. **亮度调低、夜间熄屏。** 固定放在厨房，亮度调到够看就行，不用自动亮度。晚上没人做饭时屏幕不需要亮，用系统的“定时开关机”或 Kiosk 应用的定时熄屏。
4. **可选：Fully Kiosk Browser。** V1 不做，先用 Chrome 加桌面跑；用一阵子觉得麻烦再上，见 7.4。
5. **可选：手机发菜单时点亮厨房屏。** 屏幕熄灭时网页无法自己唤醒屏幕，Fully Kiosk 提供局域网 REST 接口可以远程亮屏；API 收到“发送到厨房”时顺手调一下，厨房屏就会自己亮起来。V1 不做，进厨房点一下屏幕是完全可接受的交互。
6. **电池实在不行就换电池。** 老平板换电池的费用远低于买墨水屏；电池已鼓包的平板不要插电长期使用。

#### Screen Wake Lock API 是什么

浏览器标准 API，让网页告诉系统“我正在显示重要内容，别自动熄屏”。V1 要做，几行代码，不装任何东西：

```ts
// 有菜单时申请，菜单清空时释放
const lock = await navigator.wakeLock.request('screen');
await lock.release();
```

要点：

- 只能阻止熄屏，不能点亮已经黑掉的屏幕。所以厨房屏熄灭后手机发了菜单，屏幕不会自己亮，需要进厨房点一下。
- 页面切到后台时锁会被系统自动释放，回到前台要重新申请。
- 需要 HTTPS（或 localhost）。局域网 IP 用 HTTP 访问时不可用，和 PWA 安装是同一个前置条件，一起解决。
- 旧平板只要 Chrome 能更新到近几年的版本就支持。

### 7.4 可选：Fully Kiosk Browser

一个 Android 应用，把平板变成“只显示一个网页”的展示终端，商场自助屏、Home Assistant 挂墙面板基本都用它。可以理解为一个带了一堆运维开关的全屏浏览器。它补的正是“平板当固定屏幕”会遇到的麻烦事：

| 需求                                 | Chrome 加桌面      | Fully Kiosk                                                      |
| ------------------------------------ | ------------------ | ---------------------------------------------------------------- |
| 开机自动打开页面                     | 不行，要手点       | 可以                                                             |
| 全屏并锁住不让退出                   | PWA 可全屏，不能锁 | 可以                                                             |
| 空闲 N 分钟熄屏、点击唤醒            | 靠系统超时         | 自带，更灵活                                                     |
| 定时亮屏 / 熄屏（如 23:00–06:00 关） | 靠系统定时开关机   | 自带                                                             |
| 电量到 80% 停充、30% 开充            | 没有               | 电量触发事件 → 调智能插座的 URL                                  |
| 远程让屏幕亮起来                     | 没有               | 局域网 REST 接口 `http://平板IP:2323/?cmd=screenOn&password=...` |
| 崩溃 / 断网自动恢复                  | 没有               | 自动重载                                                         |

免费版有水印，去水印的 Plus 授权是一次性几欧元一台设备。它自带“保持常亮”选项，装了之后可以不依赖 Wake Lock；Wake Lock 是不装任何东西时的纯 Web 兜底，两者不冲突。

V1 的决定：先用 Chrome 加桌面 + 系统自带的屏幕超时和充电上限跑起来。如果之后觉得“每次开机要手点”“熄屏后手机发菜单它不亮”烦人，再装 Fully；代码侧的改动只是 API 在“发送到厨房”时多调一个 URL。门口的 TodoList 屏到时候是同一套。

### 7.3 对厨房屏界面的约束

当前已确定使用闲置Android LCD平板，厨房与手机共用可爱Memo视觉，不再为墨水屏强制黑白。未来墨水屏可再单独设计主题，不要求现在保留黑白皮肤：

- 高对比：奶油白背景、深棕文字、奶油黄主操作；当前菜同时有粗边框和文字，不能只靠色差表达状态。装饰不能挤占阅读空间。
- 字号：正文 ≥ 20px，步骤文字 24～28px，菜名 ≥ 28px；行距 1.6 以上。以竖屏约 750×1000 CSS px 为设计基准，更大的屏自然适配；平板横放时按两栏（左食材 / 右步骤）排。
- 无动画、无渐变、无骨架屏闪烁；允许轻微静态卡片阴影及小圆角。浅色只能做背景，正文仍保持清晰。
- 用翻页代替滚动；只用按钮，不做滑动手势；按钮高度 ≥ 56px，间距足够，手上有水也能点中。
- 数据未变化时不重绘 DOM，保留阅读位置、减少干扰；这与是否彩色无关。
- 有菜单时请求 Wake Lock 保持常亮，菜单清空后释放（技术说明见 TECH_STACK 第 3 节）。

## 8. UI 风格

方向：**奶油黄可爱Memo / 圆角便签**，借鉴用户参考图的温柔色块、便签卡片、柔和虚线和少量波浪边，不复制其品牌、字体资源、食物图案或“100克选择”等功能。

- 手机和厨房共用配色；厨房只放大字号、按钮并压缩装饰，不再强制黑白。页面/列表/表单/弹层/历史像同一本便签本，不分别采用不同主题。
- 奶油白底、深棕字、奶油黄标题区和按钮、白色圆角卡片；圆角16～20px、按钮14px、卡片内边距16～20px，允许轻微阴影，不用厚重拟物、纸纹、渐变或动画。
- 便签组内可用浅暖灰虚线、段落标题旁短色条、小面积波浪装饰。装饰属于CSS几何视觉，不是菜谱照片或插画功能；不要引入贴纸图片、吉祥物和字体依赖。
- 标题/菜名偏圆润友好，正文16px以上且易读，使用现有系统字体及字重；不强制手写字体，也不缩小正文追求可爱。必要错误和辅助文案不淡到看不清。
- 技术验证页S00不是正式首页；本次只更新预定设计和提示词，已实现验证页及PWA运行时主题色暂不修改。

### 10.1 V2：随机外卖（已记录，V1不实施）

V2细节待确认：支持哪些平台、粘贴纯URL还是整段分享文案、短链/跳转链接如何识别、店铺/菜品如何区分、显示名称手填还是平台可提供、重复/失效链接处理，以及外卖“换一换”的重复策略。仅保存链接并在平台打开可作为低成本起点，但自动抓取标题/菜单/价格、登录平台及链接预览不是已确认需求；不后台访问任意分享URL。链接可能含分享标识，不在日志、提示词或示例中暴露真实个人链接。

## 12. 验收标准

- 手机上可新增一道含 3 条食材（其中一条带分组）、3 个步骤、tips 的菜谱并在列表与详情中正确显示。
- 搜索菜名、按 tag 筛选结果正确；空结果有提示。
