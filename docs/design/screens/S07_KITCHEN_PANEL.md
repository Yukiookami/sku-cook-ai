# S07 发送 / 查看厨房菜单弹层设计书

状态：待实现。不是独立路由；S01 多选发送、S02 单道发送与“查看厨房菜单”共用。组件建议 `KitchenMenuPanel.vue`，出现复用后再提取。

## 1. 布局与模式

手机 Vant 底部 Popup，最大高度约视口85%，内部可滚动；平板可中宽弹窗。顶栏标题与关闭按钮，底部固定操作区。

| 模式   | 主体                                          | 操作                                   |
| ------ | --------------------------------------------- | -------------------------------------- |
| 发送   | “本次选择（N道）”按顺序列名；“厨房当前菜单”区 | 空菜单：发送到厨房；非空：替换厨房菜单 |
| 仅查看 | “厨房当前菜单”，当前菜明确标“当前查看”        | 关闭；有菜单时次级“清空厨房”           |

发送模式可取消、关闭而保留列表选择；不在弹层重新排序，新菜单顺序就是勾选顺序。当前厨房菜单是打开时读取的快照，不宣称实时在线或设备已收到。“当前查看”不是“已完成/剩余进度”。

“本次选择”每道菜有独立“− / N人份 / ＋”。详情进入带当前目标份数，列表进入默认该菜原份数（来自列表摘要），不得所有菜自动变成1人份；原份数说明显示在旁。仅查看模式显示已发送的目标份数但不提供调整按钮；目标不得低于1。

## 2. API 与交互

打开立即 [A10](../apis/A10_KITCHEN_GET.md)，手机不定时刷新；关闭后清理请求。失败保留本次选择，显示重试，禁止在未知状态发送，以免无意覆盖。空菜单文字“厨房当前没有菜单”。

发送携带读取的 expectedRevision 调 [A11](../apis/A11_KITCHEN_PUT.md)。已有菜单时主按钮明确“替换厨房菜单”，上方说明“将替换当前的 N 道菜”；这是显式确认，不再叠加模态弹窗。成功提示“厨房屏将在几秒内更新”，不提示“厨房设备已收到”。不会自动唤醒熄屏平板。

Body为items数组，每项recipeId与targetServings，不传计算后的amount；版本冲突刷新当前菜单但保留本次各菜目标，不把刷新结果覆盖成新选择份数。

409：重新读当前菜单，显示“菜单已变更，请确认后重新发送”，保留新选择，不自动提交第二次。服务端404缺少菜谱时说明已选菜被删除，回列表修正。

“清空厨房”二次确认“清空后厨房屏将回到待机，不会记录做过；菜谱和已有历史不会删除”，[A13](../apis/A13_KITCHEN_DELETE.md)成功后仅更新此弹层为空；结果不确定GET核对，不能当成功。厨房完成才通过A15记录历史，手机清空不是完成。

厨房完成后手机无通知。已经打开的弹层可以保留旧快照直至重开 / 用户点重试；提交带版本可防止旧快照误操作。关闭再开即可读新状态，不新增常驻同步逻辑。

## 4. 验收

单道/多道弹层复用；开一次只读一次（手动重试除外）；现有菜单替换明确；断网不能盲发；清空不删菜谱；完成无手机通知；冲突不自动覆写。

每道目标份数独立发送/显示；取消和冲突保留选择值；厨房清空后不修改原菜谱份数。
